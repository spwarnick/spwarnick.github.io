Overview

Lab Overview

This two-part lab built practical skills in network perimeter defense. Lab 1 used Linux iptables to design and implement a host-based firewall policy — creating rules to selectively allow or block traffic by source IP, protocol, and port, then verifying each rule with live traffic generation. Lab 2 configured a Squid forward proxy server, routed browser traffic through it, and performed log analysis on the proxy's access logs using the calamaris tool.

  • Filtered HTTP traffic by source IP
  • Controlled ICMP echo requests per-host
  • Blocked outbound traffic to Facebook by IP
  • Verified each rule with live traffic from 3 VMs
L2

Squid Proxy — Config & Log Analysis

Methodology

Methodology

Lab 1 — iptables Firewall Rules

A multi-rule iptables policy was designed and applied on the Kali Linux VM using the Apache web server as a test service. Rules were applied in order — iptables processes rules top-to-bottom and stops at the first match — making rule ordering critical to correct behavior.

ChainRuleActionPurpose
INPUT-i loACCEPTAllow all loopback traffic
INPUT-s 192.168.150.150 --dport 80ACCEPTAllow HTTP from Windows 10 VM only
INPUT! -s 192.168.150.150 --dport 80REJECTBlock HTTP from all other hosts
INPUT-s 192.168.150.150 --icmp-type echo-requestACCEPTAllow ICMP ping from Windows 10 VM
INPUT-s 192.168.150.200 --icmp-type echo-requestREJECTBlock ICMP ping from Ubuntu VM
OUTPUT-d 157.240.22.35 (Facebook)DROPBlock outbound traffic to Facebook

Each rule was verified by generating the corresponding traffic from the appropriate VM. The Windows 10 VM successfully browsed the Kali Apache page and sent pings; the Ubuntu VM was correctly blocked from both. The Facebook block was confirmed via Wireshark — outbound packets to Facebook's IP were silently dropped.

iptables Rule Creation

# Flush existing rules sudo iptables -F # Allow HTTP from Windows 10 only; reject from all others sudo iptables -A INPUT -s 192.168.150.150 -p tcp --dport http -j ACCEPT sudo iptables -A INPUT -p tcp ! -s 192.168.150.150 --dport http -j REJECT # ICMP: allow from Windows 10, reject from Ubuntu sudo iptables -A INPUT -s 192.168.150.150 -p icmp --icmp-type echo-request -j ACCEPT sudo iptables -A INPUT -s 192.168.150.200 -p icmp --icmp-type echo-request -j REJECT # Block outbound Facebook traffic sudo iptables -A OUTPUT -p tcp -d 157.240.22.35 -j DROP # List all rules sudo iptables -L

Lab 2 — Squid Proxy Configuration

Squid was configured on Ubuntu SEED to act as a forward proxy for Kali Linux. The squid.conf was modified to add a domain blacklist (facebook.com), an allowed-hosts ACL restricted to Kali's IP, cache directory settings, and combined-format access logging that captures the HTTP referrer and user-agent headers. Firefox on Kali was configured to route all HTTP traffic through the proxy at port 3128.

Key Squid Configuration Directives

# Domain blacklist ACL acl blacklist dstdomain "/etc/squid/blacklist.txt" http_access deny blacklist # Restrict proxy access to Kali Linux only acl myclients src "/etc/squid/allowed_hosts.txt" http_access allow myclients # Enable disk cache and combined access logging cache_dir ufs /var/spool/squid 100 16 256 access_log daemon:/var/log/squid/access.log combined # Parse logs with calamaris cat access.log | calamaris -a > parsed_squid_access.log

Findings

Key Findings

Finding 1 — Rule Order Is Critical in iptables

iptables processes rules sequentially and stops at the first match. Placing the Windows 10 ACCEPT rule before the broad REJECT rule was essential — reversing the order would have caused all HTTP traffic to be rejected before the Windows 10 exception could be evaluated. This underscores the importance of careful rule ordering in all stateless firewall implementations.

Finding 2 — REJECT vs. DROP Have Different Behaviors

HTTP from unauthorized hosts was set to REJECT (sends an ICMP port-unreachable response), while Facebook traffic used DROP (silently discards). REJECT gives the sender immediate feedback; DROP causes a timeout. Defenders often prefer DROP for external-facing rules to avoid revealing the firewall's presence.

Finding 3 — Squid Combined Logging Captures Rich Metadata

Switching Squid's log format to combined captured HTTP referrer and user-agent headers in addition to the basic request data. This significantly enriched the calamaris-parsed reports — making it possible to see not just what was visited, but what linked to it and what browser/tool made the request. This level of detail is invaluable for security investigations.

Finding 4 — Domain Blacklisting Is Easily Circumvented

Blocking facebook.com by domain in Squid prevents access via the domain name, but an attacker could bypass it by using Facebook's direct IP address or a non-standard domain. Production proxy deployments combine domain blacklists with SSL inspection and category-based filtering (e.g., via threat intelligence feeds) to more comprehensively enforce content policies.

Takeaways

Lessons & Takeaways

These labs built hands-on proficiency with two foundational defensive controls — host-based firewalling and forward proxy deployment. iptables remains widely used in Linux server environments and is the basis for many modern firewall tools (nftables, ufw). Forward proxies like Squid remain relevant in enterprise environments for content filtering, SSL inspection, and traffic logging.

Key takeaways: default-deny firewall policies (block everything, allow only what's needed) are far more secure than default-allow; proxy combined logging should be enabled in all environments where HTTP traffic monitoring is required; and domain-based blocking should be supplemented with IP and SSL-layer controls for meaningful enforcement.
