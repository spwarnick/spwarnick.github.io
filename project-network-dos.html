Overview

Lab Overview

This two-part lab developed core network traffic analysis and attack skills. Lab 1 used Wireshark to capture and dissect a full spectrum of network protocols — ARP, ICMP, DNS, TCP, and HTTP — building the foundational ability to read and interpret live packet captures. Lab 2 implemented three classes of Denial of Service attacks using custom Python/Scapy scripts: ICMP flood with IP spoofing, DNS amplification-style spoofed queries, and a SYN flood — all observed in real time through Wireshark.

Wireshark — Protocol Analysis

  • Captured ARP, ICMP, DNS, TCP, and HTTP traffic
  • Identified MAC/IP addresses from ARP queries & replies
  • Traced full DNS query/response for byu.edu & utah.edu
  • Followed TCP 3-way handshake and HTTP GET request
  • Identified HTTP 302 redirect and BigIP web server
L2

DoS Attacks — Scapy Scripts

  • ICMP flood with spoofed source IP via Scapy
  • DNS amplification-style attack spoofing victim IP
  • SYN flood with randomized source IPs and ports
  • All attacks verified and analyzed in Wireshark

Methodology

Lab 1 — Wireshark Protocol Analysis

Traffic was generated between Kali Linux and Ubuntu SEED using Nmap ARP and ICMP host discovery scans, DNS lookups (nslookup www.byu.edu), and browser navigation to www.utah.edu. The capture was saved and analyzed in Wireshark's Protocol Hierarchy view to enumerate all protocols present.

Lab 2 — DoS Attack Implementation

Three DoS attack scripts were written and executed using Python and Scapy, with each attack captured in Wireshark for analysis.

Attack 1 — ICMP Flood with Spoofed Source IP

A Scapy script sent ICMP echo request packets to 8.8.8.8 (Google DNS) with the source IP spoofed to 192.168.150.150 (the Windows 10 victim). Google's server responded to the victim IP — which never initiated the request — causing the victim to reply with ICMP "Destination Unreachable" messages, demonstrating the amplification and misdirection potential of spoofed ICMP floods.

ICMP Spoofed Flood (Scapy)

# Craft ICMP packet with spoofed source IP IPLayer = IP() IPLayer.src = "192.168.150.150" # Victim's IP (spoofed) IPLayer.dst = "8.8.8.8" # Destination (Google DNS) pkt = IPLayer / ICMP() send(pkt, inter=3, count=5, verbose=0)

Attack 2 — DNS Amplification-Style Attack

A similar spoofing approach was applied to DNS — sending UDP DNS queries for www.utah.edu to 8.8.8.8 with the victim's IP as the source. The DNS server sent its (larger) response back to the victim, who responded with ICMP "Port Unreachable" — illustrating the mechanics of DNS amplification attacks.

Attack 3 — SYN Flood

A SYN flood script sent TCP SYN packets to the Ubuntu SEED machine (port 80) in a continuous loop with randomized source IPs and ports. Each SYN caused the server to allocate a half-open connection and send a SYN/ACK — which was never acknowledged. With no completion, the server's connection table fills up, ultimately denying service to legitimate clients.

SYN Flood (Scapy)

# Randomized source IP and port — hard to filter by source ip.src = "192.168.150.%i" % (random.randint(1, 254)) tcp.sport = random.randint(1, 65535) tcp.dport = 80 tcp.flags = 'S' # SYN only — never completes handshake send(ip / tcp)

Findings

Key Findings

Finding 1 — Wireshark Exposes the Full Protocol Stack

A single browsing session to utah.edu generated traffic across five protocol layers simultaneously — ARP, ICMP, DNS, TCP, and HTTP. Protocol Hierarchy view in Wireshark provided an immediate inventory of all protocols present, demonstrating how a defender can quickly characterize what a host is doing from raw packet data alone.

Finding 2 — IP Spoofing Is Trivial Without Ingress Filtering

All three DoS attacks used spoofed source IPs with no obstacles. Scapy allows arbitrary IP fields to be set at packet construction time. Without BCP38 ingress filtering at the network edge, spoofed packets traverse the network undetected — enabling both traffic misdirection and amplification attacks.

Finding 3 — SYN Flood Exploits Stateful TCP Design

The SYN flood exploited TCP's requirement to maintain state for half-open connections. Each unanswered SYN consumes server resources for the SYN_RCVD timeout period.

Finding 4 — HTTP Reveals Detailed Application Fingerprints

The Wireshark capture of the HTTP GET to utah.edu exposed the client browser (Firefox), the ephemeral source port (49818), the HTTP method (GET), the response code (302 Found), and the server type (BigIP). This level of detail is available to any attacker with network visibility — reinforcing the importance of HTTPS to encrypt application-layer metadata.

Takeaways

Lessons & Takeaways

These labs built two complementary skills: the ability to read and interpret network traffic as a defender, and an understanding of how attackers manipulate low-level protocol behavior. Wireshark proficiency is foundational for SOC analysts and incident responders — the ability to quickly identify anomalous traffic patterns (duplicate SYNs, unexpected ICMP, DNS amplification spikes) is what separates fast incident response from prolonged breaches.

Key defensive takeaways: deploy BCP38 ingress filtering to block spoofed source IPs at network edges; enable SYN cookies on servers exposed to the internet; use rate limiting and anomaly detection on DNS resolvers to detect amplification abuse; and maintain Wireshark/pcap capture capabilities in lab and production environments for forensic reconstruction of incidents.
