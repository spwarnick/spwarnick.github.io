Overview

Lab Overview

This two-part lab explored Man-in-the-Middle (MITM) attack techniques at the network layer. Lab 1 used ARP poisoning to position Kali Linux between an Ubuntu victim and its default gateway, intercepting unencrypted HTTP credentials in transit. Lab 2 escalated to active session manipulation — using a custom Python/Scapy script to hijack an established TCP telnet session and inject a command that created a directory on a remote server without the legitimate user's knowledge.

L1

ARP Poisoning — Credential Interception

  • Mapped network hosts with Ettercap ARP scan
  • Poisoned ARP tables of gateway and Ubuntu victim
  • Intercepted HTTP login credentials in plaintext
  • Verified poisoning via duplicate MAC in ARP cache
L2

TCP Hijacking — Session Injection

  • Set up 3-VM environment: client, server, attacker
  • Captured live telnet session parameters in Wireshark
  • Crafted forged TCP packet with Scapy Python script
  • Injected mkdir command; confirmed on server

Methodology

Methodology

Lab 1 — ARP Poisoning with Ettercap

ARP (Address Resolution Protocol) maps IP addresses to MAC addresses on a local network. Because ARP has no authentication mechanism, any host can broadcast false ARP replies claiming to own any IP address — causing other hosts to update their ARP caches with incorrect MAC mappings.

Ettercap was used to scan the local subnet and identify active hosts. The default gateway (192.168.150.1) was set as Target 1 and the Ubuntu SEED victim (192.168.150.200) as Target 2. Ettercap then continuously sent forged ARP replies to both targets — telling the gateway that the victim's IP belonged to Kali's MAC, and telling the victim that the gateway's IP belonged to Kali's MAC.

With Kali positioned in the traffic path, the victim navigated to testphp.vulnweb.com and submitted login credentials over HTTP. Ettercap captured the plaintext username and password in real time. The poisoning was confirmed in Wireshark by observing duplicate MAC addresses — the same MAC address (Kali's) appearing for both the gateway and victim IPs in the ARP cache.

ARP Cache — Poisoning Evidence

# Pre-poisoning: each IP maps to a unique MAC 192.168.150.1 → aa:bb:cc:11:22:33 (gateway MAC) 192.168.150.200 → 08:00:27:9d:be:11 (Ubuntu MAC) # Post-poisoning: both IPs now map to Kali's MAC (08:00:27:25:b5:8f) 192.168.150.1 → 08:00:27:25:b5:8f ← Kali's MAC 192.168.150.200 → 08:00:27:25:b5:8f ← Kali's MAC (duplicate!)

Lab 2 — TCP Session Hijacking with Python/Scapy

TCP sessions are identified by a 4-tuple (source IP, source port, destination IP, destination port) and sequenced using sequence and acknowledgment numbers. If an attacker can observe these values on an active session, they can forge a packet that the server will accept as coming from the legitimate client.

A telnet session was established between Ubuntu_SEED_Client (192.168.150.200) and Ubuntu_SEED_Server (192.168.150.225). Wireshark on Kali captured the live session and revealed the exact TCP parameters needed for injection — source port, sequence number, acknowledgment number, and window size.

Session Parameters Captured from Wireshark

Source IP: 192.168.150.200 (client) Destination IP: 192.168.150.225 (server) Source Port: 50070 Destination Port: 23 (telnet) Next Sequence Num: 2707100219 Acknowledgment Num: 1550081606 Window Size: 245

The command to inject (mkdir Utah\n) was converted to its hex representation, then fed into the custom tcp_hijacking.py Scapy script along with the captured session parameters.

Command Encoding & Packet Injection

# Convert 'mkdir Utah\n' to hex for injection echo "mkdir Utah\n" | xxd | tr -d " " | tr a-z A-Z | cut -d ":" -f2 # Result: 6D6B64697220557461680A0A # Run the Scapy injection script sudo python tcp_hijacking.py # Inputs: source/dest IP, ports, seq/ack nums, flags (URG/ACK/PSH), window, hex data

The forged packet was accepted by the telnet server as a legitimate continuation of the existing session. Execution was confirmed on Ubuntu_SEED_Server — the Utah directory appeared in the seed user's home directory with a creation timestamp matching the injection, verified with stat Utah.

Findings

Key Findings

Finding 1 — ARP Has No Authentication

ARP caches are updated by any gratuitous ARP reply, regardless of whether the host requested one. This fundamental design flaw allows any attacker on the same subnet to silently redirect all traffic through their machine. The poisoned ARP cache showed Kali's MAC address (08:00:27:25:b5:8f) mapped to both the gateway and victim IPs simultaneously.

Finding 2 — Plaintext Protocols Are Completely Exposed

HTTP credentials submitted by the victim to testphp.vulnweb.com were captured by Ettercap in complete plaintext — username and password visible without any decryption. This is why HTTPS (TLS) is non-negotiable for any site handling authentication, even in a MITM position where traffic is intercepted.

Finding 3 — TCP Sequence Numbers Are Predictable Once Observed

The TCP hijacking succeeded because Wireshark allowed exact sequence and acknowledgment numbers to be read from a live session. Telnet transmits all data — including these session identifiers — in plaintext. An attacker with network visibility can craft a packet the server accepts as legitimate, executing arbitrary commands without ever authenticating.

Finding 4 — Telnet Is Fundamentally Insecure

Telnet transmits all data unencrypted, including credentials and session state. The successful hijacking of a telnet session reinforces why telnet has been entirely superseded by SSH in modern environments. SSH encrypts all session data and uses cryptographic authentication, making both eavesdropping and session injection attacks infeasible.

Takeaways

Lessons & Takeaways

These labs demonstrated how network-layer attacks can completely undermine application-layer security when the underlying protocols lack authentication. ARP poisoning requires no exploit — just local network access. TCP hijacking requires only visibility into a plaintext session. Both attacks are trivially executable against legacy protocols.

Key defensive controls: enforce encrypted protocols (HTTPS, SSH, TLS) to eliminate the value of traffic interception; implement Dynamic ARP Inspection (DAI) on managed switches to validate ARP packets against a DHCP snooping binding table; segment networks to limit the blast radius of a compromised host; and monitor for ARP anomalies using IDS rules or tools like arpwatch.
