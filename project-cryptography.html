Overview

Lab Overview

This two-part lab provided hands-on experience with the two foundational pillars of modern cryptography — symmetric and asymmetric encryption — using OpenSSL on the Linux command line. Lab 1 used AES-128 in ECB mode to encrypt and decrypt a plaintext file, verifying data integrity with MD5 hashing before and after decryption. Lab 2 used RSA to generate a public/private key pair, explore the mathematical structure of the keys, and perform asymmetric encryption and decryption of a message.

L1

AES-128 Symmetric Encryption

  • Created plaintext file and computed MD5 hash
  • Encrypted with AES-128-ECB using 128-bit hex key
  • Decrypted ciphertext back to plaintext
  • Verified integrity via matching MD5 hashes
L2

RSA Asymmetric Encryption

  • Generated 512-bit RSA public/private key pair
  • Inspected key structure (primes P1, P2, modulus N)
  • Exported public key in PEM format
  • Encrypted with public key; decrypted with private key

Methodology

Methodology

Lab 1 — AES-128 Symmetric Encryption

A plaintext file containing a secret message was created, and its MD5 hash was computed as a baseline integrity check. OpenSSL's AES-128-ECB cipher was used with a 128-bit hexadecimal key (32 hex characters × 4 bits = 128 bits) to produce a binary ciphertext file. The ciphertext was visually confirmed to be unreadable, then decrypted — and the MD5 hash of the decrypted file was compared to the original to verify no data corruption occurred.

AES-128 Encrypt, Decrypt & Integrity Check

# Compute MD5 hash of plaintext (baseline) cat plain.txt | tr -d "\n" | md5sum # Encrypt with AES-128-ECB (128-bit hex key) sudo openssl enc -aes-128-ecb \ -in plain.txt -out aes128ecb.bin \ -K 11111111111111111111111111111111 # Decrypt the ciphertext sudo openssl enc -d -aes-128-ecb \ -in aes128ecb.bin -out plain-aes128ecb.txt \ -K 11111111111111111111111111111111 # Verify integrity — hashes must match cat plain-aes128ecb.txt | tr -d "\n" | md5sum

Lab 2 — RSA Key Generation & Asymmetric Encryption

A 512-bit RSA key pair was generated using openssl genrsa. The internal structure was inspected with both -text and asn1parse flags, revealing the two large prime factors (P1 and P2) and the public modulus N. These values were manually verified using big-number calculators to confirm N = P1 × P2.

RSA Key Generation, Inspection & Encryption

# Generate 512-bit RSA key pair openssl genrsa -out public-private.key 512 # Inspect key structure (modulus, primes, exponents) openssl rsa -text -in public-private.key openssl asn1parse -in public-private.key # Export public key in PEM format openssl rsa -pubout -in public-private.key -out public.pem # Encrypt message with public key openssl rsautl -encrypt -inkey public.pem -pubin \ -in plain-secret-msg.txt -out encrypted-secret-msg.bin # Decrypt with private key openssl rsautl -decrypt -inkey public-private.key \ -in encrypted-secret-msg.bin -out decrypted-secret-msg.txt

Finding 1 — MD5 Hash Confirms Lossless Round-Trip

The MD5 hash of the decrypted AES output was identical to the original plaintext hash, confirming that AES encryption and decryption is perfectly lossless when the correct key is used. A single bit difference in the key would produce a completely different ciphertext and an unrecoverable plaintext.

Finding 2 — RSA Security Rests on Prime Factorization

Inspecting the key with ASN.1 parsing revealed the two prime factors P1 and P2 whose product forms the public modulus N. The security of RSA relies entirely on the fact that factoring N back into P1 and P2 is computationally infeasible at real-world key sizes. The 512-bit key used in this lab is considered insecure by modern standards — 2048 bits minimum is the current recommendation.

Finding 3 — ECB Mode Has Known Weaknesses

AES-128-ECB (Electronic Code Book) encrypts each block independently, meaning identical plaintext blocks produce identical ciphertext blocks. This leaks structural patterns in the data. Modern best practice uses AES-GCM or AES-CBC with a random IV to prevent pattern analysis — ECB mode is considered cryptographically weak for real-world use.

Takeaways

Lessons & Takeaways

These labs built hands-on intuition for the cryptographic primitives that underpin virtually all secure communications — TLS, SSH, PGP, disk encryption, and digital signatures all rely on AES and RSA (or their modern equivalents). Understanding how keys are structured, how encryption modes differ, and how integrity verification works is foundational for any security role.

Key takeaways for real-world application: use AES-256-GCM instead of AES-128-ECB for authenticated encryption with stronger key size and mode; use RSA-2048 or higher, or prefer elliptic curve cryptography (ECC) for equivalent security with shorter keys; always verify data integrity with a cryptographic hash after decryption; and never share private keys or reuse symmetric keys across sessions.
