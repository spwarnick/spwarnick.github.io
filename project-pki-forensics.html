Overview

Lab Overview

This two-part lab covered PKI and digital forensics. Lab 1 walked through the full PKI certificate lifecycle — generating key pairs, creating a Certificate Signing Request (CSR), operating as a Certificate Authority (CA) to sign it, and configuring Apache to serve HTTPS using the resulting certificate. Wireshark was used to contrast plaintext HTTP traffic with encrypted HTTPS. Lab 2 applied proxy log forensics to a realistic insider threat scenario — using Squid access logs to reconstruct a suspicious employee's browsing activity and build an evidence trail.

Methodology

Methodology

Lab 1 — Full PKI Certificate Lifecycle

The lab simulated a real PKI deployment in miniature. A new web server (www.somewhatsecurebank.net) was created as a clone of the insecure banking app. The server generated its own public/private key pair and produced a Certificate Signing Request encoding its identity. A separate DemoCA directory was set up to act as the Certificate Authority — it signed the CSR using OpenSSL's CA facilities, producing a valid X.509 digital certificate binding the server's public key to its identity.

PKI Workflow — Key Generation, CSR & CA Signing

# Step 1: Web server generates public/private key pair openssl genrsa -out somewhatsecurebank.keys 2048 # Step 2: Web server creates a Certificate Signing Request (CSR) openssl req -new -key somewhatsecurebank.keys \ -out somewhatsecurebank.csr # Step 3: CA signs the CSR and issues the digital certificate openssl ca -in somewhatsecurebank.csr \ -out somewhatsecurebank.crt \ -cert demoCA/cacert.pem \ -keyfile demoCA/private/cakey.pem # Step 4: Configure Apache to serve HTTPS # In somewhatsecurebank.conf — add SSL directives: SSLEngine on SSLCertificateFile /path/to/somewhatsecurebank.crt SSLCertificateKeyFile /path/to/somewhatsecurebank.keys

Wireshark captures before and after enabling SSL confirmed the transformation — HTTP traffic showed plaintext form submissions in the packet payload, while HTTPS traffic showed only encrypted TLS records with no readable content.

Lab 2 — Proxy Log Forensics: Insider Threat Case Study

The scenario: an employee suspected of IP theft was apprehended at an international airport with undeclared cash. No technology devices were found, but management authorized a forensic review of the Squid proxy logs from his last day at work. Three log files were analyzed: the raw access.log, a human-readable timestamp version (squid_access.log), and a referrer log (squid_referer.log).

Log Analysis Commands

# Parse full log report with calamaris cat access.log | calamaris -a > parsed_squid_access.log # Count Google-related hits grep -i "google" squid_access.log | wc -l # Result: 237 Google-related HTTP requests # Extract Google search terms from URLs grep -i "google" squid_access.log | grep -o 'q=[^&]*' # Count tsa.gov requests grep -i "tsa.gov" squid_access.log | wc -l # Result: 32 TSA-related HTTP requests # Find sites visited around the TSA blog URL via referrer log grep "blog.tsa.gov/2009/04" squid_referer.log

The forensic investigation reconstructed the following evidence trail from the logs:

Evidence 1 — Suspicious Domain Visits

Calamaris report identified multiple blogging and social media sites — potential channels for leaking IP to external parties — alongside a notable visit to tsa.gov.

Evidence 2 — Google Search Terms (237 hits)

Extracted search terms revealed queries for rare earth metals (vibranium, adamantium), international flight numbers, weather in Singapore, and TSA cash declaration rules.

Evidence 3 — TSA Blog Research (32 hits)

Referrer log showed the employee navigated to a TSA blog post specifically about "traveling with large amounts of cash" — directly correlated with the undeclared cash found in his luggage.

Evidence 4 — PDF Download

While on tsa.gov, the employee downloaded currency_reporting.pdf, hosted at internal IP 192.168.75.119 — a document about currency reporting requirements for international travel.

Findings

Key Findings

Finding 1 — HTTPS Completely Hides Payload Content

Wireshark captures confirmed that HTTPS traffic is opaque to passive observers — only TLS handshake metadata (server certificate, cipher suite) is visible. Without SSL inspection at the proxy layer, the content of HTTPS sessions cannot be read in transit. This is why SSL/TLS inspection proxies are used in high-security environments.

Finding 2 — PKI Trust Is Only as Strong as the CA

The self-signed CA in this lab was trusted only because it was manually installed as a trusted root. In production, browsers only trust certificates signed by recognized public CAs (DigiCert, Let's Encrypt, etc.). Self-signed certificates trigger browser warnings — making certificate authority trust management a critical operational security concern.

Finding 3 — Proxy Logs Are a Powerful Forensic Tool

The Squid combined-format logs provided a complete reconstruction of the employee's browsing timeline — including search terms embedded in Google URLs, referrer chains between sites, and specific file downloads. This level of visibility is only available because HTTP traffic passed through a logging proxy. Encrypted HTTPS traffic to Google would have obscured the search queries.

Finding 4 — Log Correlation Builds Investigative Narrative

No single log entry was conclusive. The forensic value came from correlating multiple data points — domain visits, search terms, referrer chains, and file downloads — into a coherent pattern consistent with pre-travel preparation. This mirrors real-world DFIR methodology: individual artifacts tell partial stories; correlation tells the full one.

Takeaways

Lessons & Takeaways

These labs connected two important security disciplines — cryptographic infrastructure and digital forensics — that are deeply related in practice. PKI and TLS determine what investigators can and cannot see in network traffic. Understanding both sides informs better decisions about where to deploy SSL inspection, what to log, and how to preserve forensic value while respecting privacy constraints.

Key takeaways: deploy HTTPS everywhere to protect user data in transit; use combined-format proxy logging to maximize forensic visibility for HTTP traffic; implement log retention policies that support incident investigation timelines; and treat proxy logs as a first-look forensic resource for insider threat and data exfiltration investigations before escalating to more invasive endpoint forensics.
